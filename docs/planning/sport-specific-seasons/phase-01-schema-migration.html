Phase 1: Schema Migration

Project: Sport-Specific Seasons Phase: 1 of 4 Depends on: None (first phase)

Overview

Adds sport_code and division columns to the seasons table, making each season row specific to one sport+division combination. The existing generic season rows are relabeled as MSO D1, and five additional rows are created for MSO D2, MSO D3, WSO D1, WSO D2, and WSO D3 — all seeded with the same start_date/end_date as the original row. Games and team_seasons are remapped to the correct sport-specific season. The /api/seasons CRUD endpoint is updated to accept and return the new columns.

What Will Be Built

1. New migration file

Create supabase/migrations/20260612000000_sport_specific_seasons.sql with the following steps in order:

-- Step 1: Add columns as nullable so existing rows don't violate NOT NULL
ALTER TABLE seasons
  ADD COLUMN sport_code text    CHECK (sport_code IN ('MSO', 'WSO')),
  ADD COLUMN division   smallint CHECK (division BETWEEN 1 AND 3);

-- Step 2: Mark all existing rows as MSO D1 (that is what was actually scraped)
UPDATE seasons SET sport_code = 'MSO', division = 1;

-- Step 3: Make columns NOT NULL now that every row has a value
ALTER TABLE seasons
  ALTER COLUMN sport_code SET NOT NULL,
  ALTER COLUMN division   SET NOT NULL;

-- Step 4: Drop the two existing uniqueness constraints
--   seasons_year_key   — created by the inline UNIQUE on year in the initial schema
--   seasons_label_unique — added by the season_label migration
-- Verify constraint names first if unsure:
--   SELECT conname FROM pg_constraint WHERE conrelid = 'seasons'::regclass AND contype = 'u';
ALTER TABLE seasons DROP CONSTRAINT IF EXISTS seasons_year_key;
ALTER TABLE seasons DROP CONSTRAINT IF EXISTS seasons_label_unique;

-- Step 5: Add the new compound unique constraint
ALTER TABLE seasons
  ADD CONSTRAINT seasons_label_sport_division_unique
  UNIQUE (label, sport_code, division);

-- Step 6: Expand — insert 5 new rows per existing season label
-- Copies start_date/end_date from the existing MSO D1 row for each label.
INSERT INTO seasons (label, year, start_date, end_date, sport_code, division)
SELECT
  s.label,
  s.year,
  s.start_date,
  s.end_date,
  combo.sport_code,
  combo.division
FROM seasons s
CROSS JOIN (VALUES
  ('MSO'::text, 2::smallint),
  ('MSO'::text, 3::smallint),
  ('WSO'::text, 1::smallint),
  ('WSO'::text, 2::smallint),
  ('WSO'::text, 3::smallint)
) AS combo(sport_code, division);

-- Step 7: Remap games.season_id where the game's sport_code/division
-- does not match the season's sport_code/division.
-- (No-op for current data which is all MSO D1, but correct for future safety.)
UPDATE games g
SET season_id = ns.id
FROM seasons old_s
JOIN seasons ns
  ON  ns.label      = old_s.label
  AND ns.sport_code = g.sport_code
  AND ns.division   = g.division
WHERE g.season_id = old_s.id
  AND (old_s.sport_code <> g.sport_code OR old_s.division <> g.division);

-- Step 8: Remap team_seasons.season_id similarly.
UPDATE team_seasons ts
SET season_id = ns.id
FROM seasons old_s
JOIN seasons ns
  ON  ns.label      = old_s.label
  AND ns.sport_code = ts.sport_code
  AND ns.division   = ts.division
WHERE ts.season_id = old_s.id
  AND (old_s.sport_code <> ts.sport_code OR old_s.division <> ts.division);

-- Step 9: Grant permissions on the updated table
-- (No new tables, so existing grants carry forward. No action needed.)
ℹ️ The conferences table requires no changes. Its unique constraint is (ncaa_conference_id, season_id) — since season_id now encodes sport+division, the constraint naturally separates conference records by sport. The upsert conflict key 'ncaa_conference_id,season_id' in application code is still correct.

2. Update /api/seasons CRUD endpoint

File: src/routes/api/seasons/+server.ts

POST — accept sport_code and division in the request body; validate and include them in the INSERT:

const { label, start_date, end_date, sport_code, division } = await request.json();
// Validate: sport_code must be 'MSO' or 'WSO', division must be 1/2/3
// INSERT: { label, start_date, end_date, sport_code, division }
// SELECT: 'id, label, start_date, end_date, sport_code, division'

PATCH — accept sport_code and division in the request body; include them in the UPDATE. Since the unique key is now (label, sport_code, division), these fields can legitimately change.

DELETE — no change needed; still deletes by id.

GET — add a GET handler that returns all seasons ordered by start_date DESC, selecting id, label, start_date, end_date, sport_code, division. This is used by the admin page to populate the allSeasons list. Currently the admin page loads seasons via the +page.server.ts server load — we keep that and also expose it via GET for any client-side refresh needs.

Implementation Notes

  • Run the migration against the local Supabase instance and verify with SELECT * FROM seasons ORDER BY label, sport_code, division; — you should see 6 rows per label.
  • The year column loses its UNIQUE constraint but stays in the table. It is still used by archive/ingest endpoints to build Storage file paths (e.g. MSO/1/2025/...).
  • Steps 7 and 8 in the migration are no-ops for current data (all games are MSO D1) but must be included so the migration is correct when WSO/D2/D3 data is later ingested.
  • The admin page currently loads allSeasons from the server load (+page.server.ts), not from the API. The API GET handler added here is for completeness — Phase 4 will update the admin UI.

Completion Criteria

  • Migration file exists at supabase/migrations/20260612000000_sport_specific_seasons.sql
  • After running the migration, SELECT count(*) FROM seasons returns 12 (2 original labels × 6 combinations each) or more if additional seasons exist
  • SELECT sport_code, division, label FROM seasons ORDER BY label, sport_code, division shows all 6 combinations for each label (MSO/1, MSO/2, MSO/3, WSO/1, WSO/2, WSO/3)
  • SELECT count(*) FROM seasons WHERE sport_code IS NULL OR division IS NULL returns 0
  • The old seasons_label_unique and seasons_year_key constraints are gone; seasons_label_sport_division_unique is present
  • All existing game rows still have valid season_id references (no orphaned games)
  • All existing team_seasons rows still have valid season_id references
  • POST /api/seasons with {label, start_date, end_date, sport_code, division} creates a new row and returns it with all 5 fields
  • POST /api/seasons without sport_code or division returns a 400 error
  • npm run check passes with no TypeScript errors

How to Validate

  1. Apply the migration: npx supabase db push (or equivalent for local dev).
  2. Open Supabase Studio → Table Editor → seasons. Verify 12 rows, all with non-null sport_code and division.
  3. Run: SELECT label, sport_code, division, start_date, end_date FROM seasons ORDER BY label, sport_code, division; — confirm the 6-combo pattern.
  4. Run: SELECT count(*) FROM games g LEFT JOIN seasons s ON s.id = g.season_id WHERE s.id IS NULL; — should return 0.
  5. Start dev server and navigate to /admin. Call POST /api/seasons with all 5 fields via the browser network tab or curl — confirm 201 response with sport_code and division in the response.
  6. Call POST /api/seasons with only {label, start_date, end_date} — confirm 400 response.
