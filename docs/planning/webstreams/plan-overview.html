Webstream Link Ingestion

Crawl the 374 school athletics sites you already map in roster_sources, pull the per-game “Watch” links off their schedule pages, and attach them to rows in games.

The short version

You already ingest schedules. nightly-ingest’s ?ahead=7 window puts unplayed games in the DB from the NCAA feed, and that feed is authoritative for date, time and opponent. So don’t scrape school schedules to get schedules — that would set up a second, conflicting source of truth for data you already have. Scrape them for the one thing the NCAA feed does not carry at all: media links.

The NCAA feed carries no broadcast data. Of 4,956 D1 games in the 2026 season, zero have a broadcaster_name. The column exists and /scores already renders it; nothing has ever filled it.

The links are there, and I confirmed it on live sites today — on all three platforms your roster pipeline already classifies. The plan below reuses that pipeline’s shape almost exactly.

But set expectations on volume. Sampling 849 events across 45 schools, 47% carry some watch link and 22% carry a real per-game URL — the rest point at conference landing pages. That is a floor rather than a forecast, since links get attached as fixtures approach, but this will not be a Watch button on every card. Full numbers in §02.

The schedule feed does not separate them — media.video.url carries both — so it is worth being precise about what actually turns up there. Same 387-event sidearm sample:

The failure mode this creates

Linear-TV events still carry a URL, and it is a cable-authenticated simulcast page: Big Ten Network → foxsports.com/live/btn (4 events), ACC Network → espn.com (2). A naive Watch button on those sends the viewer to a page demanding a TV-provider login. That is a worse outcome than showing no button, because it looks like a broken link rather than a cable game.

Carrier names need normalizing

The sample produced 12 distinct tv strings for about 6 actual carriers: “Big Ten Network” / “BTN”, “ACC Network Extra” / “ACCNX”, “ACC Network” / “ACCN”. Writing tv straight into broadcaster_name would put all twelve on the scoreboard. A small lookup map fixes it — about 20 entries covers the field — and tvImage’s filename (accnx-Logo, B1G_plus, uconn_plus) is a usable fallback for the 15 events where tv is blank.

02Why this is cheap: the crawl map already exists

roster_sources is not really a roster table — it is a (team, sport, season) → athletics site map, with the platform already classified and verified. For the 2026 season it holds:

  • 578 verified sources 208 MSO + 370 WSO
  • 374 distinct domains
  • 3 platforms, all parseable

A full sweep is therefore ~578 HTTP requests, not a discovery project. The hard part of this build — working out which URL belongs to which school and what software it runs — is already done and in production.

Three caveats on these numbers

They are a floor, not a forecast. This snapshot was taken on 4 September, two weeks into the season, so most of the events counted are future fixtures — schools routinely attach the stream link in the days before kickoff, so in-season coverage should run higher than 47%.

The wmt row is the least trustworthy: 6 of 10 sites are client-rendered and my probe could not read them, and the four that parsed returned 43–48 events, which is more than a soccer season — the event splitter is probably picking up other sports. Treat WMT as unmeasured.

“Deep link” here means a URL used exactly once in that school’s own schedule. It is a good discriminator but it will misfile the occasional shared link.

03The matching problem is smaller than it looks

School schedule pages carry no NCAA contest id, so links have to be matched onto games by inference. The natural key is (team_season_id, contest_date), and it is very nearly unique:

Across the 2025 and 2026 seasons, 20,386 of 20,428 (team-season, date) pairs map to exactly one game. Only 42 are doubleheaders.

So the matcher mirrors roster-match.ts: an exact key match, with a second field as confirmer rather than as the key.

  1. Key on (team_season_id, contest_date). The source row already gives you team_id, sport_code and season_id — exactly the team_seasons unique key — so sport separation is free.
  2. Confirm with the opponent name, normalized through the existing normalizeName(), against teams.name / short_name of the other side. A confirmed match is matched; a mismatch is ambiguous.
  3. Disambiguate doubleheaders with that same opponent name. This is the only case where it is load-bearing.
  4. Fall back to ±1 day only when the exact date misses and the opponent name confirms. Late-Pacific and Hawaii kickoffs can land on a different calendar date on the school’s own page than in the NCAA feed.
  5. Queue the rest. Anything unmatched or ambiguous goes to stream_entry_queue for review, never silently dropped — the same discipline as roster_entry_queue.

04ESPN as a second source — deferred

Decision: not in v1. Skipping it costs nothing on stream links, because it never supplied any. It only forgoes a better fill rate on broadcaster_name, which the school crawl already covers at ~39–49%. The section stays here because it is a clean, self-contained addition whenever you want it — no schema change.

ESPN runs a public scoreboard API for both college soccer leagues, and it answers a whole date in one call:

https://site.api.espn.com/apis/site/v2/sports/soccer/usa.ncaa.m.1/scoreboard?dates=20260905
https://site.api.espn.com/apis/site/v2/sports/soccer/usa.ncaa.w.1/scoreboard?dates=20260905

On the date I sampled, 32 of 38 men’s events (84%) carried a broadcasts / geoBroadcasts entry naming the carrier — FloSports, ESPN+, and so on.

It gives names, not URLs

I checked both the site API and sports.core.api.espn.com: neither exposes a watch URL. The links array has summary, video and odds pages, no stream. So ESPN complements the school crawl, it does not replace it — two calls a day fill broadcaster_name for ~84% of games, and the school crawl supplies the clickable link.

The case for adding it later: at 84% it roughly doubles the school sites’ own broadcaster fill rate, it makes the existing broadcaster line on /scores real for most games, and it tells you which games should have a link — which is the signal you would want to audit the crawl against. None of that is on the critical path for shipping watch links.

05Schema

Streams are a side table, not a column

A game can have a home-school link, an away-school link, a live-stats link and a radio feed, and links change as kickoff approaches. That is a one-to-many relationship with its own lifecycle, so it does not belong on games.

create table game_streams (
  id                bigserial primary key,
  game_id           bigint not null references games (id) on delete cascade,
  kind              text not null check (kind in ('video','audio','stats','tickets')),
  url               text,                    -- null when a carrier is named but no link given
  label             text,                    -- 'Watch', 'Live stats'

  -- the three independent axes (see below)
  carrier           text,                    -- normalized: 'espn_plus' | 'b1g_plus' | 'accn' | ...
  access            text not null default 'unknown'
                    check (access in ('free','subscription','tv_authenticated','unknown')),
  is_deep_link      boolean not null default false,

  source_side       text not null check (source_side in ('home','away')),
  roster_source_id  bigint not null references roster_sources (id),
  external_event_id text,                    -- Sidearm game id / WMT entity-id
  first_seen_at     timestamptz not null default now(),
  last_seen_at      timestamptz not null default now(),
  unique (game_id, kind, coalesce(url, carrier))
);
create index game_streams_game_idx on game_streams (game_id);

Three axes, deliberately independent

is_deep_link is about the URL’s specificity — does it point at this game? access is about what the viewer needs to watch — nothing, a subscription, or a cable login. carrier is who is showing it. They do not correlate: a B1G+ per-game link is deep and paywalled; foxsports.com/live/btn is generic and cable-gated; a school’s own /showcase?Live=7307 is deep and free. Collapsing any two of these loses information you need to decide what to render.

url is nullable now because 35 of 387 sampled events named a carrier without giving a link. Those rows are still worth keeping — they are how /scores says “on ACC Network” for a game with nothing to click.

Why is_deep_link earns its place

Butler’s schedule page labels its games “Watch (ESPN+)” but every link points at espn.com/search/_/q/butler/o/watch — a search page, not a broadcast. NC State and Virginia publish real per-game player URLs. Both are worth storing, but only one is worth surfacing as a Watch button, so classify at ingest: a URL carrying an event or video id is a deep link; a bare search or channel page is not.

The carrier map

A static lookup, not a table — it is code, it changes rarely, and it belongs next to the parsers so it is unit-tested with them. Roughly 20 entries covers what the sample turned up:

// src/lib/server/carriers.ts
export const CARRIERS = {
  'espn+':               { carrier: 'espn_plus',  access: 'subscription' },
  'espn plus':           { carrier: 'espn_plus',  access: 'subscription' },
  'b1g+':                { carrier: 'b1g_plus',   access: 'subscription' },
  'btn+':                { carrier: 'b1g_plus',   access: 'subscription' },
  'acc network extra':   { carrier: 'accnx',      access: 'subscription' },
  'accnx':               { carrier: 'accnx',      access: 'subscription' },
  'flosports':           { carrier: 'flosports',  access: 'subscription' },
  'youtube':             { carrier: 'youtube',    access: 'free' },
  'big ten network':     { carrier: 'btn',        access: 'tv_authenticated' },
  'btn':                 { carrier: 'btn',        access: 'tv_authenticated' },
  'acc network':         { carrier: 'accn',       access: 'tv_authenticated' },
  'accn':                { carrier: 'accn',       access: 'tv_authenticated' },
  // school-run services ('UConn+', 'Friars Live', ...) -> { school_stream, subscription }
};

Resolution order at ingest: the tv string through this map; failing that the tvImage filename; failing that the URL host (bigtenplus.com → b1g_plus, youtube.com → youtube). Anything unrecognized lands as carrier: null, access: 'unknown' and shows up in the admin surface as a prompt to add a map entry — that is how the map stays current without a migration.

One preferred link per game

Preference order matters more now: a free school stream should beat a cable-gated network page even though both are “a video link”.

create view game_primary_stream as
select distinct on (game_id)
       game_id, url, carrier, access, label, is_deep_link, source_side
from   game_streams
where  kind = 'video' and url is not null
order  by game_id,
          is_deep_link desc,
          array_position(array['free','subscription','unknown','tv_authenticated'], access),
          (source_side = 'home') desc,
          last_seen_at desc;

grant select on game_primary_stream to anon, authenticated, service_role;

The page must not query this view

DISTINCT ON over the whole table is fine for admin and reporting, but a planner is free to materialize it before applying a game_id filter, which turns a scoreboard render into a full scan. /scores should instead do what it already does for pick’em: a second query against game_streams filtered by .in('game_id', ids) on the ≤100 games already on screen, folded in client-side. The view stays for humans, not for the hot path.

For the same reason, do not add game_streams to the supabase_realtime publication. Stream links are set hours ahead and never change mid-match; games is in the publication because scores do.

Don’t forget the view grant

Grants on the underlying table do not cascade to a view. Without the explicit grant select … to service_role, the edge functions read an empty view and nothing errors.

Extend roster_sources rather than fork it

A parallel schedule_sources table would duplicate the domain and platform columns and immediately start drifting from the roster one. Add the schedule fields to the existing row instead:

alter table roster_sources
  add column sidearm_schedule_id  text,        -- NextGen scheduleId
  add column schedule_path        text,        -- '/sports/msoc/schedule'
  add column schedule_status      text not null default 'unverified',
  add column schedule_verified_at timestamptz;

The table’s name becomes a little narrow for what it holds. That is a smaller cost than two mappings that disagree about which platform a school runs.

Queue and log

stream_entry_queue (unmatched schedule events, mirroring roster_entry_queue) and stream_scrape_log (one row per source per run, mirroring roster_scrape_log). RLS on all three: public read on game_streams since it is display data; authenticated-only on the queue and log.

06Pipeline

Three edge functions, deployed verify_jwt:false and checking the service-role bearer themselves, exactly like the roster trio. Targeting on all three: ?source= | ?team= | default = every source with status='verified'.

schedule-discovery

On demand — resolves the schedule address per source, once per season.

For sidearm: fetch /api/v2/Sports, match the soccer entry by title and gender, store its scheduleId. For sidearm-html and wmt: probe the slug variants (mens-soccer, msoc, womens-soccer, wsoc), keep whichever returns a page with parseable events, store it as schedule_path. Sets schedule_status. This is the direct analogue of roster-discovery, including the sport-slug variance that already bites there.

stream-scrape

Fetch and archive only — no parsing, no writes to game tables.

Fetch the schedule JSON or HTML and archive it verbatim to a new private schedule-raw bucket at {sport}/{year}/{teamId}.{json|html}. The archive is the point: when a parser bug turns up you re-run the ingest against Storage instead of hitting 374 schools again.

It must be batched, not one long sweep. roster_scrape_log puts the real cost at 2.28s per source on average, 61.8s at worst. A 578-source sweep is therefore ~22 minutes of wall clock — far past an edge function’s budget. So: take ?limit= (default ~40) and a cursor, work a bounded slice per invocation, and let the cron fire it repeatedly until the season’s sources are covered. Every fetch gets an AbortController at ~15s.

stream-ingest

Read the archive, parse, match, upsert. No external fetches.

Parse per platform — parseSidearmSchedule (JSON), parseSidearmHtmlSchedule, parseWmtSchedule (both node-html-parser) — then run the matcher from §03, classify each link’s provider and deep-link status, and bulk-upsert game_streams on (game_id, kind, url), touching last_seen_at. Unmatched events land in stream_entry_queue. Writes one stream_scrape_log row per source.

The tv field the schedule pages carry alongside the video link should be written to games.broadcaster_name in the same pass — it is already in the payload you are parsing, and it fills a column that is empty today. Write it through the carrier map (§05), not raw, or the scoreboard ends up showing “BTN” and “Big Ten Network” as if they were different networks. A separate ESPN pass (§04) is deferred.

Keep the parsers pure and unit-tested

Follow the roster-match.ts precedent: parsers and matcher live in src/lib/server/ as pure functions with Vitest coverage, and the edge functions inline a copy. This is the one part of the pipeline where a silent logic bug produces plausible-looking wrong links rather than an error.

07Cron

Two new pg_cron jobs, both via pg_net with the existing edge_service_key Vault secret, slotted in after the jobs that already run at 08:00–08:15 UTC.

JobScheduleScope
stream-sync30 8 * * *Full sweep: scrape + ingest every verified source for the current season
stream-sync-gameday0 15 * * *Only sources with a game in the next 72h — catches links posted the morning of
espn-broadcasts—Deferred (§04); broadcaster_name comes from the schedule tv field instead

Daily is the right cadence. Stream links are published days ahead and change rarely; nothing here justifies the per-minute treatment the live score job needs. Both jobs must no-op in the off-season the way nightly-ingest does — resolve the season covering today and return early if there isn’t one.

08Phases

Ordered by dependency. Each is independently shippable and leaves the site working.

  1. Schema and storage foundation

    game_streams, stream_entry_queue, stream_scrape_log, the roster_sources columns, the schedule-raw bucket, the game_primary_stream view, grants and RLS.

  2. Parsers and matcher, with tests

    Three pure parsers plus matchScheduleEvents in src/lib/server/, unit-tested against archived fixtures from NC State, Butler and Virginia — the three pages I already pulled. No network, no DB.

  3. schedule-discovery

    Resolve sidearm_schedule_id / schedule_path for all 578 sources. Expect a failed tail on the slug variants and the SPA-only WMT sites; work it manually the way the roster tail was worked.

  4. stream-scrape + stream-ingest

    The two edge functions. Run against one conference first, read stream_scrape_log and the queue, then widen.

  5. Cron

    Schedule both jobs. Watch the first week’s stream_scrape_log before trusting the output.

  6. Surfaces

    Render by access, not just by presence of a URL: a Watch link for free and subscription (badged with the carrier, so “ESPN+” sets the expectation of a paywall before the click); plain text like on ACC Network for tv_authenticated and for carrier-without-URL rows, with no link at all. An admin coverage page under /admin mirroring /admin/roster: per-source last run, link counts, queue depth, share of upcoming games with a deep link, and unrecognized carrier strings awaiting a map entry.

09Traps

Most of these are lessons your existing pipelines already paid for. They apply here unchanged.

Concurrent writes to shared rows deadlock
The 30-wide backfill fan-out that produced 72 deadlocks is the precedent. Here the writes are per-game so contention is lower, but keep concurrency at 8 and let one invocation walk the source list rather than firing many invocations at once.
A 200 does not mean it worked
Per-source errors get caught and logged, exactly as in nightly-ingest. Judge a run by stream_scrape_log, never by the HTTP status.
PostgREST truncates at 1000 rows, silently
A season is ~5,000 games. Every read that can exceed 1000 rows must paginate explicitly. This one is not hypothetical: roster-scrape’s resolveTargets selects status='verified' with no pagination, and there are 1,157 such rows — so it is already silently skipping ~157 sources on a default run. Do not copy that function’s target resolution.
Edge functions have a wall clock; sequential loops blow it
The roster functions iterate targets with a plain sequential for loop. At the measured 2.28s per source that is fine for a handful and impossible for 578. Batch with a limit and cursor (§06) rather than assuming concurrency that the reference implementation does not actually have.
No fetch in the existing pipeline has a timeout
roster-scrape, roster-ingest and nightly-ingest contain zero AbortControllers, which is why the log has a 61.8s single-source worst case — a remote site hanging with nothing to cut it off. One unresponsive school should cost 15 seconds, not a whole run.
Stay clear of the every-minute live job
nightly-ingest-live runs on * * * * *. Long transactions or a saturated connection pool during a stream sweep would make those invocations stack up. Keep writes in small batches, hold no long transactions, and keep the 08:30 UTC slot — 4:30am ET, when the live gate is guaranteed asleep.
Sport slugs vary per site
Already known from rosters, where Syracuse only answers msoccer. Schedule paths vary the same way — Penn State serves /sports/mens-soccer/schedule and 404s on /sports/msoc/schedule, while Virginia is the reverse. Probe the variants; don’t assume.
Some WMT sites have no server-rendered data
South Carolina and Kentucky are XHR-only for rosters. Expect the same schools to fail here, and let them fail into the queue rather than special-casing them.
Link rot
last_seen_at is what makes this manageable: a link the school has removed stops being touched, so a stale-link sweep is a date comparison. Consider hiding a video link that has not been seen in 14 days.
Be a good guest
374 domains, one polite pass a day, a real User-Agent, capped concurrency. That is a rounding error against these sites’ normal traffic — and it stays that way only if the cadence stays daily.

10Three calls I’d like your read on

I’ve picked a default for each, so this is buildable as written — say the word if you’d rather go the other way.

  1. Both sports, or men’s first? The plan covers MSO and WSO together, since the source map already does. Default: both.

  2. Show non-deep links? Butler-style generic search URLs are honest but low-value. Default: store them, don’t surface them — the view already sorts deep links first, so this is a filter, not a schema change.

  3. Take the ESPN broadcaster pass now or later? Settled: later. It supplies names, never URLs, so deferring it costs nothing on links.

The open question the numbers in §02 raise is a product one, not an engineering one: at roughly one game in five carrying a real per-game link, is a Watch button worth shipping on a card where it is usually absent? My read is yes — the alternative is zero, the rate should climb as fixtures approach, and the same crawl fills the broadcaster line for about half of games regardless. But that is your call to make, and it is worth making before phase 6 rather than after.
