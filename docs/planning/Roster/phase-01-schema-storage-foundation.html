Phase 1: Schema & Storage Foundation

Project: Roster Phase: 1 of 7 Depends on: None (first phase)

Overview

This phase lays the database and storage groundwork for everything that follows: the table that maps each team to its external athletics roster source, new season-scoped columns on player_seasons for the data we'll collect, the staging table for roster entries that need human review, a run log, and the private Storage bucket that will hold raw roster JSON as the source of truth. It also seeds one verified source (NC State Men's Soccer) by hand so the fetch and matching phases that follow are immediately testable without waiting on bulk auto-discovery (Phase 5).

What Will Be Built

A single forward-only SQL migration under supabase/migrations/ (timestamped to sort after the latest existing migration), plus a Storage bucket migration following the existing pattern. Specifically:

1. roster_sources table

One row per (team_id, sport_code, season_id), mapping an internal team-season to its external athletics roster.

roster_sources (
  id                bigserial primary key,
  team_id           bigint   not null references teams(id),
  sport_code        text     not null,          -- 'MSO' for this project
  season_id         bigint   not null references seasons(id),
  domain            text,                         -- e.g. 'gopack.com'
  platform          text     not null default 'unknown', -- 'sidearm' | 'presto' | 'custom' | 'unknown'
  sidearm_roster_id text,                         -- e.g. '426'
  status            text     not null default 'unverified', -- 'verified' | 'unverified' | 'failed'
  last_verified_at  timestamptz,
  notes             text,
  created_at        timestamptz default now(),
  unique (team_id, sport_code, season_id)
)

2. New columns on player_seasons

Add the season-scoped roster fields. class_year already exists and must NOT be re-created.

alter table player_seasons
  add column headshot_url text,
  add column height       text,   -- store raw e.g. "5-8" or "6-1"; do not parse now
  add column hometown     text,
  add column roster_source_id bigint references roster_sources(id),
  add column roster_synced_at  timestamptz;
📝 Why on player_seasons, not players: headshot, height, hometown, and class year are all properties of a player on a specific team in a specific season (they change with transfers and years). This mirrors how class_year, jersey_number, and position already live on player_seasons.

3. roster_entry_queue staging table

Holds external roster entries that could NOT be confidently matched to an existing player_season (unmatched or ambiguous), for human review in Phase 4. Stores the raw external fields verbatim plus the matcher's suggestion.

roster_entry_queue (
  id               bigserial primary key,
  roster_source_id bigint not null references roster_sources(id),
  team_season_id   bigint not null references team_seasons(id),
  -- raw external fields (verbatim from Sidearm)
  first_name       text,
  last_name        text,
  jersey_number    smallint,
  position         text,
  class_year       text,
  height           text,
  hometown         text,
  headshot_url     text,
  external_ref     text,            -- Sidearm player id if present, else null
  -- matcher output
  match_status     text not null,   -- 'unmatched' | 'ambiguous'
  suggested_player_season_id bigint references player_seasons(id),
  suggestion_reason text,
  review_status    text not null default 'pending', -- 'pending' | 'approved' | 'rejected'
  reviewed_at      timestamptz,
  created_at       timestamptz default now(),
  unique (roster_source_id, first_name, last_name, jersey_number)
)

4. roster_scrape_log table

One row per source per run (mirrors scrape_log / reconciliation_log): records fetch/match outcomes so runs are auditable and surfaced in /admin (Phase 4).

roster_scrape_log (
  id                bigserial primary key,
  roster_source_id  bigint references roster_sources(id),
  status            text not null,   -- 'success' | 'error'
  http_status       int,
  entries_seen      int default 0,
  matched           int default 0,
  enriched          int default 0,
  queued            int default 0,   -- unmatched/ambiguous staged
  error_message     text,
  duration_ms       int,
  created_at        timestamptz default now()
)

5. Storage bucket

A private bucket sidearm-raw-rosters, created with the same idempotent INSERT ... ON CONFLICT DO NOTHING pattern as the existing bucket migration.

6. Grants / RLS

Match the established convention: GRANT ALL on the new tables and their sequences to service_role; GRANT SELECT to anon, authenticated; enable RLS with public-read policies. (The review/queue tables are written only by the service role; reads can stay admin-gated at the app layer.)

7. Seed NC State

Insert one verified roster_sources row for NC State Men's Soccer in the current season: domain='gopack.com', platform='sidearm', sidearm_roster_id='426', status='verified'. Look up team_id via the existing teams.ncaa_team_id (seoname) and the active season via the seasons table. This unblocks Phases 2–4.

Implementation Notes

  • Follow the existing migration conventions exactly — see the files in supabase/migrations/ for naming (YYYYMMDDHHMMSS_description.sql), grant style, and RLS policy style.
  • The height column stays raw text on purpose — parsing (and nationality) are explicitly out of scope for this project.
  • Do not add a headshot download/storage step — we store the external URL only.
  • The seed must resolve team_id and season_id dynamically (subselects), not hardcode IDs, so it is portable across environments.

Key files to read before starting

  • supabase/migrations/20260610000000_ncaa_raw_bucket.sql — the exact bucket-creation pattern to mirror for sidearm-raw-rosters.

Completion Criteria

  • roster_sources, roster_entry_queue, and roster_scrape_log tables exist with the columns above.

  • Grants and RLS policies match the existing convention (service_role full; anon/authenticated select; RLS enabled).

How to Validate

  1. Apply the migration. Confirm success with no errors.
  2. Run select table_name, column_name from information_schema.columns where table_name in ('roster_sources','roster_entry_queue','roster_scrape_log') and confirm the schema.
  3. Run select column_name from information_schema.columns where table_name='player_seasons' and confirm the five new columns plus the pre-existing class_year.
  4. Run select id, name from storage.buckets where id='sidearm-raw-rosters' — expect one row.
  5. Run select rs.*, t.name from roster_sources rs join teams t on t.id=rs.team_id — expect exactly the NC State row, correctly joined to the teams table, status verified.
