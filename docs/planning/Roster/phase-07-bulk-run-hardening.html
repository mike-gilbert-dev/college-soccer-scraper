Phase 7: Bulk Run, Coverage & Hardening

Project: Roster Phase: 7 of 7 Depends on: Phase 6 complete
⚠️ Prerequisite: Phase 6 (Source Auto-Discovery) must be complete — the bulk run executes against the verified sources it produced.

Overview

With discovery done, this phase runs the full pipeline across all verified D1 Men's Soccer sources, adds the coverage reporting needed to operate it, and hardens the edge cases that only surface at scale. It turns the proven NC State pipeline into a repeatable, observable bulk operation and is the final polish pass before the project is considered shippable.

What Will Be Built

1. Bulk run (three steps)

Confirm the full pipeline runs cleanly across all status='verified' sources for the active season, as the three separate steps the project is built around:

  1. Bulk scrape — roster-scrape default mode fetches and archives raw JSON for every verified source, with bounded concurrency and politeness delays.
  2. Bulk ingest — roster-ingest default mode reads each archived file back from Storage, matches, enriches, and stages the remainder for every team (no external HTTP).
  3. Bulk headshots — roster-headshots default mode downloads images for matched players whose source URL is new/changed and stores them by season-scoped path.

All three steps must be resumable/idempotent so a re-run only updates. Because ingest reads from Storage, the matching pass can be re-run across all teams without re-scraping; and headshot download skips unchanged images so routine re-runs only fetch new/changed photos.

2. Coverage reporting

An admin coverage view answering: per team and overall — how many player_seasons have an enriched headshot URL, a downloaded headshot (headshot_path), class, and hometown; how many roster entries are still pending review; which verified sources failed their last run. A read view or SQL function (mirror the get_games_missing_player_stats style) backs the panel.

3. Edge-case hardening

  • Duplicate names on one team (two players, same normalized name): ensure they route to ambiguous/review rather than enriching the wrong row.
  • Jersey conflicts: roster jersey differs from box-score jersey — log, don't clobber.
  • Missing/partial fields: players with no headshot/height/hometown enrich the fields that exist; nulls don't overwrite existing non-null data.
  • Schema drift / non-2xx / empty roster: fail that source gracefully with a roster_scrape_log error row; one bad source never aborts the batch.
  • Off-season / no active season: no-op safely, consistent with the NCAA pipeline.
  • Stale sources: a previously verified source that now 404s is logged and surfaced, not silently skipped.

4. Operator documentation

Add a section to CLAUDE.md (matching the existing pipeline docs) covering: the roster pipeline architecture and its three-step scrape→ingest→headshots split, the roster-scrape / roster-ingest / roster-headshots manual triggers and their query params, the discovery pass, the admin review/coverage surfaces, and the non-Sidearm fallback list.

Implementation Notes

  • Politeness at scale matters most here — keep concurrency modest and add per-request delay; this hits ~200 external sites in one run.
  • Every source's outcome must be independently logged; the batch is fault-isolated.
  • Reconciliation philosophy holds throughout: never clobber players.name; only fill null season fields from box scores; roster is authoritative for headshot/height/hometown/class_year.
  • No new scheduling is added (on-demand decision stands); document how to invoke instead.

Completion Criteria

  • A full bulk run completes across all verified sources without aborting; per-source outcomes are all logged.
  • Coverage view reports headshot/class/hometown fill rates per team and overall, plus pending-review and failed-source counts.
  • Each hardening edge case has a defined, tested behavior (duplicate names → review; jersey conflict → logged; partial fields → partial enrich; bad source → isolated error).
  • A second full run is idempotent (no duplicate queue rows, stable enrichment).
  • CLAUDE.md documents the roster pipeline, triggers, and admin surfaces.
  • npm run check passes.

How to Validate

  1. Run the bulk scrape, then the bulk ingest, then the bulk headshots. Confirm roster_scrape_log has rows covering every verified source and that no unhandled exception aborted any batch.
  2. Open the coverage view; confirm fill-rate numbers look plausible and match spot SQL checks.
  3. Find a team with two same-named players (or simulate one) and confirm both route to review, not mis-enrichment.
  4. Temporarily point a verified source at a 404 URL and re-run; confirm an isolated error row and the rest of the batch still completes.
  5. Run the batch twice; confirm idempotency (queue + enrichment stable).
  6. Review the new CLAUDE.md section for accuracy against what was built.
