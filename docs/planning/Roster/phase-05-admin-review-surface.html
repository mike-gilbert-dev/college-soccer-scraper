Phase 5: Admin Review Surface

Project: Roster Phase: 5 of 7 Depends on: Phase 3 complete (independent of Phase 4)
⚠️ Prerequisite: Phase 3 (Matching Engine) must be complete — this phase resolves the entries it stages in roster_entry_queue.

Overview

The matcher deliberately stages anything uncertain instead of guessing. This phase gives a human the tools to clear that queue: a /admin section that lists unmatched and ambiguous roster entries, shows the matcher's suggestion alongside the candidate internal players, and lets the reviewer approve (link or create) or reject each one. It also surfaces per-source run history so the operator can see coverage at a glance. This mirrors the existing /admin → Data → Reconciliation surface.

What Will Be Built

1. Resolution RPCs / server actions

Server-side handlers (SvelteKit form actions or +server.ts, admin-gated) that resolve a queued entry:

  • Approve → link existing: attach the queue entry to a chosen existing player_season (the suggestion or a manually picked one); apply the same enrichment Phase 3 applies to confident matches; set review_status='approved', reviewed_at=now().
  • Approve → create new: for a genuine roster-only player, mint a players row (synthetic ncaa_player_id in the same {teamId}_{first}_{last} format via get_or_create_players), create the player_season for the team-season, enrich it, and mark the queue entry approved.
  • Reject: set review_status='rejected' (e.g., duplicate, staff, or bad data); excluded from future re-queueing.
📝 Creating players happens only on explicit human approval — this is the safety guarantee behind the "stage for review" decision. The matcher itself never auto-creates.

2. Admin UI — roster review page

A new page under the existing admin area (e.g. src/routes/admin/.../roster/+page.svelte + +page.server.ts), Svelte 5 runes mode. It shows:

  • A queue list filtered to review_status='pending', grouped by team, showing the external entry (name, jersey, position, class, hometown, headshot thumbnail) and match_status.
  • For ambiguous entries: the suggested internal player plus other same-team candidates, each with an Approve action.
  • For unmatched entries: a "Create new player" action and a search/typeahead to link to an existing player_season instead.
  • A Reject action on every row.

3. Run history / coverage panel

A read-only view of recent roster_scrape_log rows (per source: entries_seen / matched / enriched / queued / status / time), so the operator can see which teams have been ingested and how clean the match was — analogous to the Reconciliation panel.

Implementation Notes

  • Reuse the existing admin auth gating and layout — do not invent a new auth path. Read the current admin Data pages first and match their structure, component usage (Flowbite Svelte tables), and form-action conventions.
  • All files outside node_modules must use runes ($props, $state, $derived) per CLAUDE.md.
  • Resolution actions are mutations — run them server-side with the admin/secret client, never from the browser client.
  • Approve/Reject must be idempotent and safe against double-submits (check current review_status before acting).

Completion Criteria

  • An admin-gated roster review page lists pending roster_entry_queue entries grouped by team.
  • Approve→link attaches the entry to an existing player_season and enriches it; the queue row becomes approved.
  • Approve→create mints a player + player_season (via get_or_create_players) and enriches it; the queue row becomes approved.
  • Reject marks the entry rejected and it no longer appears in the pending list (and is not re-queued on the next ingest).
  • A run-history/coverage panel shows recent roster_scrape_log rows.
  • All new Svelte files use runes mode; npm run check passes.
  • Non-admin users cannot reach the page or trigger the actions.

How to Validate

  1. After a Phase 3 NC State run, open the admin roster review page; confirm the pending NC State entries appear with thumbnails and suggestions.
  2. Approve→create on a genuine freshman: confirm a new players + player_seasons row appears, enriched, and the queue entry flips to approved.
  3. Approve→link on an ambiguous entry: confirm it attaches to the chosen player_season and enriches it.
  4. Reject one entry; re-run roster-ingest for NC State and confirm the rejected entry is not re-queued.
  5. Log out / use a non-admin session and confirm the page and actions are inaccessible.
