Phase 3: Matching Engine (External → player_seasons)

Project: Roster Phase: 3 of 7 Depends on: Phase 2 complete
⚠️ Prerequisite: Phase 2 (Roster Scrape & Archive) must be complete — this phase reads the archived raw JSON back from Storage; it never re-fetches the external site.

Overview

This is the core of the project, and it is built as a separate function from the scraper (Phase 2). Scraping wrote raw JSON to Storage; this phase's roster-ingest function reads that JSON back via readStoredRoster, then connects each external roster entry to the correct internal player_season, enriches confident matches with the collected fields, and stages everything uncertain for human review. Keeping ingest separate from scrape means the matcher can be re-run against already-scraped files without touching the external site. The key enabling insight is that internal players are themselves created from firstName/lastName scoped to a team_season (from NCAA box scores), with a jersey_number on player_seasons — the exact shape Sidearm provides. So matching is a normalized-name join within a single team_season, with jersey number as a confirmer/disambiguator.

What Will Be Built

1. Name normalization + matcher — src/lib/server/roster-match.ts

A pure matching module:

  • normalizeName(s) — lowercase, strip diacritics (NFD + remove combining marks), drop punctuation, collapse whitespace. Reuse/extend the normalization idea from syntheticPlayerId() in nightly-reconcile so it is consistent with how internal names were keyed.
  • matchRoster(parsed, existingPlayerSeasons) — given the parsed external entries and the existing player_seasons for the team-season (joined to players.name, jersey_number), classify each external entry.

2. Match classification rules

For each external entry, against the team-season's existing player_seasons:

ConditionResultAction
Exactly one normalized full-name matchmatched (confident)Enrich that player_season
Name match + jersey number also matchesmatched (confirmed)Enrich that player_season
Multiple internal players share the normalized nameambiguousStage; if jersey resolves to one, record it as suggested_player_season_id
No full-name match, but a unique last-name + jersey matchambiguousStage with suggestion + reason (likely nickname/first-name variant)
No plausible match at allunmatchedStage with no suggestion (likely roster-only player, e.g. freshman)
📝 Jersey is a confirmer, not a primary key. A confident name match still applies even if the jersey differs (jerseys change between/within seasons) — but a jersey mismatch on an otherwise-confident match is recorded in the log for visibility.

3. Enrichment writes (confident matches only)

For confident matches, update the matched player_seasons row, setting headshot_url (the external source URL only — the actual image is downloaded later in Phase 4), height, hometown, class_year, roster_source_id, and roster_synced_at = now(). Never touch players.name (preserve externally-normalized names, consistent with the get_or_create_players philosophy). Do not overwrite an existing non-null jersey_number/position from box scores unless null — roster and box-score sources should reconcile, not clobber; when in doubt, leave existing values and only fill nulls.

4. Staging writes (unmatched / ambiguous)

Upsert each non-confident entry into roster_entry_queue (verbatim raw fields + match_status + suggestion). The UNIQUE(roster_source_id, first_name, last_name, jersey_number) constraint makes re-runs idempotent — a queued entry is updated, not duplicated. Do not re-queue an entry whose review_status is already approved/rejected.

5. The ingest runner — edge function supabase/functions/roster-ingest/index.ts

A new, separate on-demand edge function (distinct from Phase 2's roster-scrape). It accepts the same targeting params (?team= / ?source=, default all verified sources for the active season) and for each target: reads the archived roster JSON from Storage via readStoredRoster (no external fetch), runs parseRoster, loads the team-season's existing player_seasons, runs the matcher, applies enrichment, stages the remainder, and records counts (matched, enriched, queued) in roster_scrape_log. If no archived file exists for a target, it logs and skips (the source must be scraped first). Use batched upserts (follow the Phase A/B/C batching in nightly-reconcile) and copy the nightly-ingest auth/structure (verify_jwt:false, Bearer service-key check, season resolution, JSON summary).

Implementation Notes

  • Resolve the correct team_season_id from the source's team_id + season_id + sport_code (the team_seasons unique key).
  • The matcher must be a pure function over inputs (parsed entries + existing rows) so it can be unit-tested without a DB.
  • Idempotency is required: running the same roster twice yields the same enrichments and the same queue, with no duplicates.
  • Keep all matching within a single team-season — never match across teams.
