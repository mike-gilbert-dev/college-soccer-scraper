Phase 6: Source Auto-Discovery & Verification

Project: Roster Phase: 6 of 7 Depends on: Phase 5 complete
⚠️ Prerequisite: Phases 1–5 complete — discovery populates roster_sources, which the scrape/ingest pipeline already consumes, and the unresolved tail is corrected in the admin surface (Phase 5).

Overview

Phases 1–4 work against hand-seeded sources. This phase scales the team→website mapping out across all D1 Men's Soccer teams: bootstrap candidate athletics domains from a structured source, auto-resolve each team's Sidearm roster ID, verify the mapping against live data, and leave the unresolved tail for manual fix. There is no clean rule from team name to domain, so this is treated as populating slowly-changing reference data, not runtime resolution.

What Will Be Built

1. Domain bootstrap

A one-time discovery pass that proposes a candidate domain for each teams row (D1 MSO) from a structured external source. Choose the most reliable available source at build time — candidates, in rough order of preference:

  • Wikidata (SPARQL): university/athletics program → "official website".
  • Learfield/Sidearm client directory: most target schools on one vendor list.
  • NCAA team pages (the API the pipeline already speaks) if they expose an official-site link.

Join candidates to internal teams on teams.ncaa_team_id (seoname) — the stable key — not display name. Write candidates into roster_sources with status='unverified'.

2. Roster-ID resolution

For each candidate domain, fetch the public roster page https://{domain}/sports/mens-soccer/roster and extract the /api/v2/Rosters/{id} reference the page uses (the same call confirmed via DevTools for gopack.com). Set sidearm_roster_id and platform='sidearm' on success. If no such reference is found, set platform to 'presto'/'custom'/'unknown' as detectable and leave status='failed' — these become the non-Sidearm fallback list (out of scope to scrape, in scope to flag).

3. Auto-verification

For each resolved (domain, roster_id), fetch the Sidearm JSON and assert the mapping is correct before trusting it: the response's displayTitle/school fuzzy-matches the internal team name, and the player count is sane (≈15–40). On pass, set status='verified' and last_verified_at. On mismatch, set status='failed' with a notes explanation. This is what prevents a wrong-domain match from polluting player data downstream.

4. Discovery runner + admin tail

  • An admin-triggered runner (edge function or admin +server.ts) that executes bootstrap → resolve → verify across all teams with bounded concurrency and politeness delays, writing progress/outcomes.
  • Extend the Phase 5 admin surface with a roster_sources management view: filter by status, see verified/failed/unverified counts, and manually set/correct domain, sidearm_roster_id, platform, and status for the tail.
📝 Target outcome is ~80–90% auto-verified; the remainder is a short manual session in the admin tail view. Domains rarely change, so this is mostly a one-time cost per season.

Implementation Notes

  • Be polite to third-party sites: bounded concurrency (reuse pool()), a real User-Agent, and a small delay; this pass touches ~200 external sites.
  • Roster IDs are per-sport-per-season — store them on the season-scoped roster_sources row and expect to re-resolve each new season.
  • Verification must be conservative: prefer marking failed (human reviews) over a false verified.
  • If using Wikidata/SPARQL or HTML extraction, keep the bootstrap source pluggable so it can be swapped without touching the resolve/verify steps.
  • The fetch+match pipeline already only consumes status='verified' rows, so a bad candidate cannot reach player data until verified.

Key files to read before starting

  • supabase/functions/nightly-reconcile/index.ts — pool() bounded concurrency for the multi-site pass.
  • The Phase 5 admin pages — extend them with the sources-management view.

Completion Criteria

  • The discovery runner populates roster_sources for all D1 MSO teams with a status on each.
  • A clear majority (target ≥80%) reach status='verified' with a resolved domain + sidearm_roster_id.
  • Verification rejects deliberately wrong mappings (test: point a row at the wrong domain → it ends failed, not verified).
  • Non-Sidearm schools are flagged (platform ≠ sidearm, status='failed') rather than silently dropped.
  • The admin sources view lists statuses and allows manual correction of the tail.
  • npm run check passes.

How to Validate

  1. Run the discovery pass. Inspect select status, count(*) from roster_sources group by status — confirm the verified share meets target.
  2. Spot-check 10 verified rows: open https://{domain}/api/v2/Rosters/{id} and confirm it returns the correct school's roster.
  3. Confirm the pre-existing NC State seed remains verified and is not duplicated.
  4. Manually corrupt one row's domain and re-verify — confirm it flips to failed.
  5. In the admin sources view, correct a failed row's domain/ID and confirm it can be re-verified to verified.
