Phase 2: Username UI & Account Tools

Project: Pick'em Phase: 2 of 7 Depends on: Phase 1 complete
⚠️ Prerequisite: Phase 1 (Vitest Harness & Username Backend) must be complete — this phase consumes set_username, username_available, and src/lib/username.ts.

Overview

Builds every screen that touches usernames: the signup field, the account settings page, and the one-time confirmation prompt for the three backfilled accounts. Also removes email addresses from the UI now that a display identity exists.

After this phase, identity is complete and the rest of the project is purely about picks.

📄 See pickem.md — "Why username_is_generated exists" explains the confirmation prompt's purpose; "Public read surfaces" covers the email-removal decision.

What Will Be Built

1. Register form — src/routes/register/

Add a username field above the email field. The server action must pass it through to Supabase as user metadata so Phase 1's trigger can consume it:

await locals.supabase.auth.signUp({
  email, password,
  options: { data: { username } }
});

Before calling signUp, the action validates with validateUsername() and checks username_available(), returning fail(400, ...) with a specific message. It must also catch Postgres error 23505 from the trigger's unique index and map it to "That username was just taken — try another", since a small race exists between the availability check and the insert.

Live availability feedback: debounce ~400ms, call username_available via the browser client, show ✓ / ✗ inline. Run validateUsername() locally first so format errors never cost a round trip.

2. /account — new route, auth-gated

+page.server.ts redirects to /login when there's no user, and loads the current profile (username, username_changed_at, username_is_generated). Sections:

  • Username — current name, a change form, and the cooldown state. When a change isn't yet allowed, disable the input and show the date it unlocks rather than only failing on submit.
  • Email — display current address, form to change it via supabase.auth.updateUser({ email }), with a note that confirmation is required.
  • Password — change via supabase.auth.updateUser({ password }). Reuse PasswordInput.svelte.

Use SvelteKit form actions here (not fetch) — these are low-frequency, benefit from progressive enhancement, and match the pattern already used by /login and /register.

3. Confirm-your-username prompt

For profiles where username_is_generated = true. Shown as a dismissible-but-persistent banner in the root layout (not a blocking modal — it must not prevent browsing). Copy should make the situation plain:

Your display name is @ilgilbert30, generated from your email address. It won't appear publicly until you confirm or change it. [Keep it] [Change it]

"Keep it" calls set_username with the current name (flipping the generated flag without starting the cooldown). "Change it" links to /account.

✅ This is the privacy mechanism, not decoration. A generated name is derived from the user's email local-part. Until the user has seen this prompt, that string must not appear on any public surface — which Phase 1's public_profiles view already enforces at the data layer.

4. Navbar — replace email with username

src/lib/components/Navbar.svelte renders page.data.user.email in two places (desktop dropdown, mobile menu). Both become @{username}. Add an Account link to the dropdown next to the existing Admin link.

This requires username in PageData: extend src/routes/+layout.server.ts to include it. src/hooks.server.ts already fetches the profile row for is_admin — extend that existing query to select username, username_is_generated too and expose them on locals, rather than adding a second round trip per request.

Implementation Notes

Svelte 5 runes mode is enforced. Use $props(), $state(), $derived() — never export let or legacy stores. See CLAUDE.md.

Extend the existing hooks query, don't add another. hooks.server.ts runs on every request and already does one profiles select via supabaseAdmin. Adding columns is free; adding a query is not.

Don't add /account to the sitemap. Per CLAUDE.md, auth pages and internal routes stay out of sitemap.xml.

Email confirmation flow. Changing an email in Supabase sends a confirmation link and does not take effect until confirmed. The UI must say so, or users will think it silently failed.

Completion Criteria

Every item below must be satisfied before proceeding to Phase 3.

  • Registering requires a username; submitting without one shows a validation error and creates no account
  • Registering with a taken username fails gracefully with a readable message, not a raw Postgres error
  • Live availability feedback appears while typing and correctly reports taken vs. available
  • A newly registered account has username_is_generated = false and the chosen username
  • /account redirects anonymous visitors to /login
  • /account allows a username change, and the old name appears in username_history
  • A second username change within 30 days is blocked in the UI with the unlock date shown
  • Email and password changes both work from /account
  • The confirmation banner appears for the 3 backfilled accounts and not for new signups
  • "Keep it" clears username_is_generated without setting username_changed_at, and the banner disappears
  • No email address is rendered anywhere in the navbar on desktop or mobile
  • An Account link is present in the user dropdown
  • npm run check passes with no new type errors

How to Validate

  1. npm run dev, go to /register. Type ilgilbert30 → expect a "taken" indicator. Type ab → "too short". Type admin → "reserved".
  2. Register a fresh account with a valid username. Confirm in SQL: select username, username_is_generated from profiles order by id desc limit 1; → the chosen name, false.
  3. Sign in as that account. Navbar dropdown shows @username, no email, and an Account link.
  4. At /account, change the username. Verify username_history gained a row and username_changed_at is set.
  5. Attempt a second change immediately — the form should be disabled with the unlock date, and the RPC should return 'cooldown' if called directly.
  6. Sign in as one of the 3 backfilled accounts. The confirmation banner appears. Click "Keep it" — banner clears, username_is_generated is false, username_changed_at is still null.
  7. Confirm that account now appears in select * from public_profiles.
  8. Change the email; confirm Supabase sends a confirmation mail and the UI says confirmation is pending.
  9. Run npm run check and npm run test.
