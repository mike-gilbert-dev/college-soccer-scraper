Phase 4: Pick Controls on the Scoreboard

Project: Pick'em Phase: 4 of 7 Depends on: Phase 3 complete
⚠️ Prerequisite: Phase 3 (Picks Schema, RLS & Kickoff Lock) must be complete — the RLS lock must be verified before any UI can be trusted to respect it.

Overview

The first user-facing Pick'em phase. Adds the three-way pick control to every unstarted game card on /scores, an API endpoint to persist picks, and loading of existing picks so a returning user sees their selections.

At the end of this phase the game is playable — picks are made and stored, just not yet graded. Grading lands in Phase 5, which is why validation here is about persistence and the lock, not about correctness of results.

📄 See pickem.md — "Routes and UI → The pick control on a game card" has the card layout sketch and the reasoning for fetch over form actions.

What Will Be Built

1. POST / DELETE /api/picks

New route src/routes/api/picks/+server.ts.

  • POST — body { gameId: number, outcome: 'home'|'draw'|'away' }. Upserts on the (user_id, game_id) conflict target. 401 if unauthenticated. Returns the stored pick.
  • DELETE — body { gameId: number }. Removes the pick.
✅ Use locals.supabase, never supabaseAdmin. The whole security model depends on these writes running under the user's JWT so Phase 3's RLS policies apply. Using the service-role client here would silently bypass the kickoff lock and defeat the feature. When RLS rejects a write, translate it into a 403 with "This game has already started" rather than leaking the Postgres error.

2. Load existing picks — src/routes/scores/+page.server.ts

After the games query, when a user is present, one additional query:

const { data: picks } = await supabase
  .from('picks')
  .select('game_id, outcome, result')
  .in('game_id', games.map(g => g.id));

Return as a Record<gameId, {outcome, result}> map for O(1) lookup in the template. Skip the query entirely for anonymous visitors. RLS already scopes it to the current user, so no user_id filter is needed — but include one anyway for index use and clarity.

3. PickControl.svelte

New component in src/lib/components/. Props: the game, the current pick (if any), and whether the viewer is signed in. Renders three states:

  • Signed in, game open — a pick affordance on each team row plus a slim Draw bar between them. Selected = filled primary (#e8463a); unselected = outline.
  • Signed out, game open — a muted "Sign in to pick" link to /login?redirect=/scores.
  • Game locked — renders the user's pick read-only if they made one, nothing otherwise.

Interaction: clicking an unselected outcome picks it; clicking the selected one clears it. Update local $state optimistically, fire the request, and revert on failure with a brief inline error.

4. Wire into the scoreboard card

The scheduled-game card has no score in the right-hand column, so the pick controls occupy that space and the card's two-row rhythm is preserved.

⚠️ The card body is a role="link" that navigates to the box score. Every pick control must call e.stopPropagation() or picking will also navigate away. The team links in scores/+page.svelte already do exactly this — follow that existing pattern.

Implementation Notes

Why fetch and not form actions. A busy October Saturday renders 100+ cards; form actions would mean 300+ <form> elements with use:enhance. The page already runs client-side JS for realtime scores, so a single endpoint plus local state is both lighter and more responsive. (Phase 2's /account uses form actions precisely because it is the opposite case — low frequency, benefits from progressive enhancement.)

Respect the existing realtime $effect. scores/+page.svelte keeps games in local $state re-seeded from data.games on navigation. Pick state must survive that re-seed — either key it separately from the games array or re-seed it in the same effect. Getting this wrong makes picks appear to vanish when changing date.

A game can lock while the page is open. A user sitting on the scoreboard at kickoff can still see a control the server will now reject. That's acceptable — RLS is authoritative — but the 403 must present as a clear "this game has started" message, not a generic failure. Optionally re-derive open/closed from isGameOpen() (Phase 3) on the realtime tick.

Accessibility. Pick controls are real <button> elements with aria-pressed reflecting selection and an aria-label naming the team and game. Keyboard users must be able to pick without triggering the card's navigation.

Mobile. The scoreboard is dense and heavily used on phones — controls need a ≥32px touch target without making cards taller. Verify at 375px width.

Completion Criteria

Every item below must be satisfied before proceeding to Phase 5.

  • Signed-in users see three pick controls (home / draw / away) on every unstarted game card
  • Clicking an outcome persists it and it survives a page reload
  • Clicking the selected outcome clears the pick
  • Switching from one outcome to another updates rather than duplicating the row
  • Picking does not navigate to the box score
  • Picks persist correctly when navigating between dates and back
  • Started, live, final, postponed and cancelled games show no pick controls
  • Signed-out visitors see a "Sign in to pick" affordance that preserves the return path
  • A POST for an already-started game returns 403 with a readable message
  • An unauthenticated POST returns 401
  • Controls are keyboard operable and expose aria-pressed
  • Cards remain usable at 375px width with touch targets ≥32px
  • Anonymous page loads issue no picks query
  • npm run check passes with no new type errors

How to Validate

  1. npm run dev, sign in, and go to /scores with a 2026 date that has scheduled games — ?date=2026-08-12 is the season's first slate.
  2. Pick the home team on one game, the draw on another, the away team on a third. Reload — all three persist with the right selections.
  3. Click a selected control to clear it. Reload — it's gone.
  4. Confirm in SQL: select game_id, outcome, season_id, sport_code from picks where user_id = '<uuid>'; — season_id and sport_code populated by the trigger.
  5. Click directly on a pick control and confirm the page does not navigate to the box score. Then click the card body and confirm it does.
  6. Navigate to another date and back; picks still render.
  7. Switch to Women's and confirm picks work there too and don't bleed across sports.
  8. Sign out. The same page shows "Sign in to pick"; clicking it lands on /login and returns to /scores after signing in.
  9. Lock enforcement: force a game to look started — 
    update games set start_time = now() - interval '1 hour' where id = <id>;
    reload, confirm the control is gone, then curl the endpoint directly for that game and confirm a 403.
  10. Tab to a pick control and activate with Enter/Space — it picks without navigating.
  11. Open devtools at 375px and confirm card density and touch targets.
  12. Run npm run check and npm run test.
