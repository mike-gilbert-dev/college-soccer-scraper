Phase 1: Vitest Harness & Username Backend

Project: Pick'em Phase: 1 of 7 Depends on: None (first phase)

Overview

Establishes two foundations at once: the repo's first automated test setup, and the username identity layer that every public Pick'em surface depends on. Usernames come first because leaderboards and profile pages need a stable, non-email display identity, and because making the column NOT NULL is far cheaper with three existing accounts than it will be later.

This phase is backend-only — no UI. Phase 2 builds the screens that drive these RPCs.

📄 See pickem.md — the "Data model → profiles" and "Security model → Username changes go through an RPC" sections contain the agreed DDL, the username_is_generated rationale, and the reserved-word list.

What Will Be Built

1. Vitest harness (new to this repo)

Add vitest as a dev dependency and configure it inside the existing vite.config.ts (a test block — no separate config file). Add scripts to package.json:

"test":       "vitest run",
"test:watch": "vitest"

Tests live beside the code as *.test.ts. This phase only needs the node environment — no jsdom, no component testing, no new Svelte testing libraries. Keep the footprint minimal; the goal is testable pure logic, not a full UI test rig.

2. src/lib/username.ts — shared validation module

A dependency-free module used by the client (live availability feedback), the server action, and the tests. It must not import anything from $app or Supabase so it stays trivially testable.

export const USERNAME_MIN = 3;
export const USERNAME_MAX = 20;
export const USERNAME_PATTERN = /^[A-Za-z0-9_]{3,20}$/;
export const RESERVED_USERNAMES: readonly string[] = [ ... ];

export type UsernameError =
  | 'too_short' | 'too_long' | 'invalid_chars' | 'reserved';

/** Returns null when valid, otherwise the reason it failed. */
export function validateUsername(raw: string): UsernameError | null;

/** Email local-part -> candidate username. Used by the backfill and tests. */
export function deriveUsernameFromEmail(email: string): string;

Reserved list: admin, administrator, moderator, mod, staff, support, system, root, null, undefined, anonymous, deleted, collegesoccer, csio, ncaa. Compare case-insensitively.

3. Migration — supabase/migrations/<ts>_profiles_username.sql

Follow the exact DDL in the reference doc:

  • Add username text, username_changed_at timestamptz, username_is_generated boolean not null default false to profiles.
  • Backfill from auth.users.email local-part, setting username_is_generated = true.
  • alter column username set not null + format check constraint.
  • Unique index on lower(username).
  • Create username_history table + lookup index.
  • Replace handle_new_user() to read new.raw_user_meta_data->>'username'.
✅ Backfill verified against the live database. All 3 existing accounts derive to valid, non-colliding usernames (lengths 11, 8, 15; all alphanumeric; all confirmed). No disambiguation suffix or length padding is required. Re-run the verification query before applying — if any new account has been created since, the backfill needs a collision suffix.

4. RPCs

Both security definer with set search_path = '', granted execute to authenticated:

  • username_available(p_username text) returns boolean — false if taken, or if held in username_history within 30 days by a different profile.
  • set_username(p_username text) returns text — returns 'ok' | 'taken' | 'reserved' | 'invalid' | 'cooldown'. Validates format and reserved words, enforces the 30-day cooldown, writes the old name to username_history, updates the profile, sets username_changed_at, and clears username_is_generated. All in one transaction.
✅ Confirming a generated username must not start the cooldown. When username_is_generated is true, set_username skips the cooldown check and leaves username_changed_at null — a user must not be locked into a name they never chose.

5. public_profiles view

create view public.public_profiles as
  select id, username from public.profiles where not username_is_generated;
grant select on public.public_profiles to anon, authenticated;

Implementation Notes

Do not grant UPDATE on profiles to authenticated. The table holds is_admin; a direct update grant would let any user escalate privileges or bypass the cooldown. All writes go through set_username. The existing grants (SELECT to authenticated, ALL to service_role) stay exactly as they are.

Views need their own grants. Table-level grants do not cascade to views in this project — public_profiles needs its own explicit GRANT SELECT or it will 401 for anon and authenticated alike.

Duplicated validation is intentional. The rules live in both src/lib/username.ts and the SQL check constraint. TS gives fast feedback and testability; SQL is the security backstop that a crafted request cannot bypass. If the rules change, change both — the tests should assert the pattern string matches the constraint.

handle_new_user runs on every auth.users insert. With username NOT NULL, a signup that supplies no username metadata will fail at the trigger. Phase 2's register form always supplies one. If a future OAuth or magic-link flow is added, the trigger needs a generated fallback rather than raising — noted as a known risk in the reference doc.

  • Confirming a generated username succeeds and does not set username_changed_at
  • public_profiles excludes rows where username_is_generated is true, and is readable by anon
  • authenticated still has no UPDATE grant on profiles
  • CLAUDE.md updated: test commands documented, "no test suite" line removed

How to Validate

  1. Run npm run test — all username module tests pass.
  2. Before applying the migration, re-run the backfill verification: 
    select u.email, lower(regexp_replace(split_part(u.email,'@',1),'[^A-Za-z0-9_]','','g')) as derived
from auth.users u order by u.created_at;
    Confirm every derived value is 3–20 chars and all are distinct.
  3. Apply the migration (npm run db:push, or db:reset locally).
  4. Confirm the backfill: 
    select id, username, username_is_generated, username_changed_at from public.profiles;
    Expect 3 rows, all with usernames, all username_is_generated = true, all username_changed_at null.
  5. Exercise the RPCs as an authenticated user (Supabase SQL editor with a set request.jwt.claims, or via the browser client once Phase 2 exists):
    • select username_available('ILGILBERT30') → false (case-insensitive collision)
    • select username_available('brandnewname') → true
    • select set_username('admin') → 'reserved'
    • select set_username('ab') → 'invalid'
    • select set_username('validname') → 'ok'; re-run with another name → 'cooldown'
  6. Confirm select * from public_profiles returns only profiles whose username has been confirmed.
  7. Attempt update profiles set is_admin = true as an authenticated non-admin — must be denied.
