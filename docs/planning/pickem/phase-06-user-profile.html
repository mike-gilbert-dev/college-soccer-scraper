Phase 6: User Profile & Season Chart

Project: Pick'em Phase: 6 of 7 Depends on: Phase 5 complete
⚠️ Prerequisite: Phase 5 (Automatic Grading) must be complete — this page displays graded results and has nothing to show without them.

Overview

The personal stats surface: a public profile at /u/[username] showing a user's record, their recent picks, and a season-long chart of their cumulative performance against the field average.

The aggregate functions built here are also what Phase 7's leaderboard builds on, so the security pattern established in this phase — security definer functions exposing totals only — matters beyond this page.

📄 See pickem.md — "Public read surfaces" defines the three RPC signatures and, importantly, why the chart's "average" is the pooled field rate rather than a mean of per-user percentages.

What Will Be Built

1. get_user_pick_summary(p_username, p_season_id, p_sport_code)

security definer, granted to anon and authenticated. Returns wins, losses, voids, graded count, win %, season rank, best streak and current streak.

Win % denominator is wins + losses — voids are excluded, never counted as losses.

2. get_pick_timeline(p_username, p_season_id, p_sport_code)

One row per date on which the user has a graded pick:

contest_date, user_wins, user_losses,
user_cum_wins, user_cum_pct, field_cum_pct
✅ field_cum_pct is the pooled rate — all users' cumulative wins ÷ all users' cumulative graded picks up to that date. Not the mean of individual users' percentages. With a handful of users early in a season, a per-user mean swings wildly on tiny samples; pooled is stable from the first week. This is a deliberate decision, not an implementation detail.

3. /u/[username] route

+page.server.ts resolves the username via public_profiles (so unconfirmed generated usernames 404), then calls both RPCs. Season and sport are query params defaulting to the current season and MSO, matching the /scores convention.

Page sections:

  • Header — @username, W-L record, win %, rank
  • Chart — cumulative win % vs. field average over the season
  • Recent picks — a table of the last ~25 graded picks: date, matchup, picked outcome, actual result, ✓/✗
  • Empty state — for a user with no graded picks yet, pointing at /scores

4. PickPerformanceChart.svelte

A hand-rolled SVG line chart following the existing pattern in PlayerFormChart.svelte — two series (user, field), a responsive ResizeObserver width, hover cross-highlighting, light/dark aware. No new charting dependency.

5. Navigation and SEO

  • Add My Picks to the navbar user dropdown, linking to the signed-in user's own profile.
  • Add <meta name="robots" content="noindex"> to the profile page.
  • Do not add /u/ pages to sitemap.xml.
⚠️ User pages are public but deliberately unindexed. They're shareable by link — that's the point — but individual users shouldn't become search results. This is consistent with the privacy stance behind username_is_generated.

Implementation Notes

Aggregates must not leak individual picks. The RPCs return only the requested user's own pick history plus aggregate field numbers. No function in this phase may return another identifiable user's individual picks — particularly not on unstarted games. Phase 3's RLS already prevents direct reads; don't reopen that hole through a security definer function.

Views and functions need explicit grants. Table grants don't cascade in this project. Every function needs grant execute ... to anon, authenticated or the page 401s for logged-out visitors.

Paginate the recent-picks query. PostgREST caps responses at 1000 rows and truncates silently. The recent-picks list is explicitly limited, but any future "all picks" view must paginate.

Rank ties. Use rank(), not row_number() — two users on identical records should share a rank rather than being ordered arbitrarily.

Chart edge cases that must not crash the page: a user with one graded pick (single point, no line), a user whose picks are all voids (0 graded — show the empty state), and the very first date of the season where the field average has a tiny denominator.

How to Validate

  1. Seed a realistic history: insert picks for 2–3 test users across many 2025 dates with a mix of wins, losses, draws and voids, then run grade_picks().
  2. Visit /u/<username> and cross-check the header against SQL: 
    select count(*) filter (where result='win')  as wins,
       count(*) filter (where result='loss') as losses,
       count(*) filter (where result='void') as voids
from picks p join public_profiles pp on pp.id = p.user_id
where pp.username = '<username>';
    Confirm win % = wins / (wins + losses).
  3. Verify the chart's final field-average point equals the pooled rate: 
    select count(*) filter (where result='win')::numeric
       / count(*) filter (where result in ('win','loss')) from picks;
  4. Hover the chart — cross-highlighting works and values match the table.
  5. Toggle dark mode; confirm both series stay legible.
  6. Resize to 375px; the chart and table remain usable.
  7. Visit a nonexistent username → 404. Visit a backfilled account that hasn't confirmed → 404.
  8. Create a user with exactly one graded pick → page renders. Create one with only voids → empty state.
  9. Switch season to 2024 and sport to WSO; all sections update coherently.
  10. Sign out and reload — the page still renders. View source and confirm noindex.
  11. Fetch /sitemap.xml and confirm no /u/ entries.
  12. Clean up test picks. Run npm run check and npm run test.
