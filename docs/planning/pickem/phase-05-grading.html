Phase 5: Automatic Grading

Project: Pick'em Phase: 5 of 7 Depends on: Phase 4 complete
⚠️ Prerequisite: Phase 4 (Pick Controls) must be complete — grading needs real picks to grade, and the result badges attach to the cards built there.

Overview

Turns stored picks into records. Adds the grade_picks() function, schedules it, and surfaces win/loss on the scoreboard cards.

This is the highest-risk phase in the project: a silent bug here corrupts every user's record and every leaderboard downstream, and nobody notices until the numbers are already wrong. It is also the most verifiable — the 2025 season provides 5,276 finished games with known outcomes to test against.

📄 See pickem.md — "Data model → Grading" has the function body, the shootout/cancelled/postponed decisions, and the rationale for a stored result column over a computed view.

What Will Be Built

1. grade_picks()

A security definer SQL function that updates every pick whose stored result disagrees with the current game state, returning the number of rows changed. Rules:

  • final with scores → compare actualOutcome to picks.outcome → win or loss
  • shootout → the score is tied, so the outcome is draw; do not consult the shootout winner
  • cancelled → void
  • postponed → leave ungraded; the row keeps its id and grades when the game is eventually played
  • scheduled / live → leave ungraded
✅ Idempotency is the safety property. The where result is distinct from <computed> clause means re-running is a no-op unless something actually changed — which is also how a corrected score self-heals. The function must be safe to run every minute forever. Verify by running it twice and asserting the second call returns 0.

2. Schedule — pg_cron, pure SQL

select cron.schedule('grade-picks', '*/10 * * * *',
                     $$select public.grade_picks()$$);

No edge function, no HTTP, no Vault secret — grading is pure SQL, so it needs none of the machinery the ingest pipeline requires. Every 10 minutes self-gates to nothing when there's nothing to grade, and resolves picks within minutes of a final rather than waiting for the 08:00 UTC nightly chain.

3. Result badges on scoreboard cards

Extend PickControl.svelte's locked state to show the graded outcome: a ✓ for a win, ✗ for a loss, and a muted "void" for cancelled games. The user's picked outcome stays visible so the card reads as "you picked the draw, and you were right."

4. Instant client-side result on live finals

The scoreboard already patches game rows via Supabase Realtime. When a game flips to final in an open tab, derive the result immediately with actualOutcome() from src/lib/picks.ts rather than waiting up to 10 minutes for the cron. The stored result remains authoritative on reload; this is presentation only.

5. Vitest coverage

Extend src/lib/picks.test.ts with a gradePick(outcome, game) helper mirroring the SQL, covering every branch: correct home/draw/away, incorrect, shootout-as-draw, cancelled, postponed, and ungraded states.

6. Backfill

Run grade_picks() once after deploying to grade any picks made during Phase 4.

Implementation Notes

The SQL is authoritative; the TS mirrors it. Two implementations of the same rules is a real risk — they can drift. The TS exists only for instant UI feedback. Any rule change must land in both, and the SQL wins on reload. Consider a comment in each pointing at the other.

Validate against 2025, not synthetic data. The 2025 season has 5,276 finals including 1,149 draws and 68 shootouts. Insert synthetic picks across a representative sample and assert grading matches independently-computed expectations — this catches sign errors and shootout mishandling that hand-written fixtures miss.

Watch for a subtle draw bug. home_score = away_score is NULL — not true — when both are null, so ungraded games correctly fall out of the comparison. Make sure the case expression checks home_score is not null before treating equal scores as a draw, or a scoreless scheduled game could grade as a draw.

Don't chain this to the ratings cron. Grading is independent of ratings and much cheaper; a separate 10-minute job is simpler and fails independently.

Completion Criteria

Every item below must be satisfied before proceeding to Phase 6.

  • grade_picks() exists and returns a count of rows graded
  • Correct picks grade to win, incorrect to loss
  • A pick of draw on a drawn game grades to win
  • A shootout game grades as a draw — a draw pick wins, a team pick loses
  • Cancelled games grade to void; postponed games stay ungraded
  • Scheduled and live games stay ungraded
  • Running grade_picks() twice in a row grades 0 rows the second time
  • Correcting a game's score and re-running flips the affected picks
  • The grade-picks cron job is registered and visible in cron.job
  • Graded picks show ✓ / ✗ on the scoreboard card with the picked outcome still visible
  • A live game going final in an open tab shows the result without a reload
  • Vitest covers every grading branch and passes
  • CLAUDE.md documents the new cron job alongside the existing ones

How to Validate

  1. Apply the migration and confirm the job: 
    select jobname, schedule, command from cron.job where jobname = 'grade-picks';
  2. Bulk validation against 2025. Insert one synthetic pick per outcome across a sample of 2025 finals, run grade_picks(), then verify against an independent computation: 
    select p.result,
       case when g.home_score > g.away_score then 'home'
            when g.away_score > g.home_score then 'away'
            else 'draw' end = p.outcome::text as should_be_win,
       count(*)
from picks p join games g on g.id = p.game_id
where g.status = 'final'
group by 1, 2;
    Every row must be win/true or loss/false. Any win/false or loss/true is a bug.
  3. Draw coverage: confirm picks on the 1,149 drawn 2025 games grade correctly — draw picks win, team picks lose.
  4. Shootout coverage: pick both the shootout winner and the draw on a shootout game; the draw wins and the team pick loses.
  5. Idempotency: run select grade_picks(); twice — second call returns 0.
  6. Score correction: change a final game's score, re-run, confirm affected picks flip and graded_at updates.
  7. Cancelled: set a game to cancelled, re-run, confirm void.
  8. Postponed: set a game to postponed, re-run, confirm it stays ungraded; set it back to final and confirm it grades.
  9. UI: load /scores on a date with graded picks and confirm ✓/✗ badges.
  10. Realtime: with /scores open, update a picked game to final with a score in SQL; the badge appears without reload.
  11. Clean up all synthetic picks: delete from picks where user_id = '<test-uuid>';
  12. Run npm run test and npm run check.
