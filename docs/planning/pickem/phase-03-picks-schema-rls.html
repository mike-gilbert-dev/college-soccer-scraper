Phase 3: Picks Schema, RLS & Kickoff Lock

Project: Pick'em Phase: 3 of 7 Depends on: Phase 2 complete
⚠️ Prerequisite: Phase 2 (Username UI) must be complete — picks are attributed to a user identity that must already be publishable.

Overview

Creates the picks table and — more importantly — the security model that makes the game fair. The kickoff lock is enforced in Row Level Security, not in the UI, because a lock that only exists in the client is not a lock.

This phase writes no application code. It ends with a database that will reject a late pick from any client, which is the invariant everything else rests on.

📄 See pickem.md — "Data model → picks" has the full DDL and the rationale for storing an outcome rather than a team id; "Security model → Pick lock, enforced in RLS" has the policies verbatim.

What Will Be Built

Migration — supabase/migrations/<ts>_picks.sql

1. Enums and table

create type pick_outcome as enum ('home', 'draw', 'away');
create type pick_result  as enum ('win', 'loss', 'void');

Then the picks table exactly as specified in the reference doc, with unique (user_id, game_id) and the three indexes (picks_user_season_idx, picks_game_idx, and the partial picks_ungraded_idx for the grader).

✅ Picks store an outcome, never a team id. This is deliberate: it makes 2-way vs. 3-way a config difference rather than a migration, and it avoids depending on team_seasons.id, which migration 20260609000001_split_team_seasons_by_sport.sql has already rewritten once. A pick must survive that kind of change.

2. Denormalization trigger

A before insert trigger fills season_id and sport_code from the referenced game. The client never supplies them, so it cannot mis-attribute a pick to the wrong season or sport to game a leaderboard.

3. game_is_open(p_game_id bigint)

create or replace function public.game_is_open(p_game_id bigint) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (
    select 1 from public.games g
     where g.id = p_game_id
       and g.status = 'scheduled'
       and coalesce(g.start_time,
                    (g.contest_date::timestamp at time zone 'America/New_York')) > now()
  );
$$;

Must be security definer — it is called from an RLS policy and needs to read games regardless of the caller.

✅ The coalesce fallback is a safety net, not a hot path. Verified against the live database: 0 of 5,279 D1 2025 games had a null start_time. The fallback locks a TBD-time game at midnight ET on game day, which errs toward locking early — the correct direction for integrity.

4. RLS policies

Enable RLS, grant select, insert, update, delete to authenticated, and add the four policies from the reference doc. Every one of insert/update/delete is gated on both auth.uid() = user_id and game_is_open(game_id).

Users can only ever select their own picks. Aggregate visibility (leaderboards, other users' profiles) arrives in Phases 6–7 via security definer functions that expose totals only.

5. Vitest coverage

Extract the outcome-derivation logic into src/lib/picks.ts so it is unit-testable and shared with the client (Phase 5 uses it for instant result feedback on live score updates):

export type PickOutcome = 'home' | 'draw' | 'away';

/** Which outcome actually occurred. Null when the game has no final score. */
export function actualOutcome(
  game: { home_score: number | null; away_score: number | null; status: string }
): PickOutcome | null;

/** Whether a game can still be picked, given a reference time. */
export function isGameOpen(
  game: { status: string; start_time: string | null; contest_date: string },
  now?: Date
): boolean;

Test both against the draw, shootout, and boundary cases listed below. This TS logic must stay in lockstep with the SQL — the SQL remains authoritative.

Implementation Notes

Shootouts are draws. A PK-decided game keeps its tied score, and the site already treats it as a tie in W-L-T records, Elo and RPI (see 20260723000000_games_shootout.sql). actualOutcome must therefore return 'draw' for a shootout game and must not consult shootout_winner_team_season_id. Grading it any other way would contradict every other page on the site. 68 of 5,276 games in 2025.

Do not add a foreign key to team_seasons. There is no team reference on a pick by design — see the note above.

The lock is absolute and has a consequence worth recording: any game that kicks off before this feature ships is permanently unpickable. The 2026 season's first game is 2026-08-12. Games played during the build window will simply have no picks — expected, not a bug.

Non-D1 opponents are pickable. Some games on a D1 slate involve a non-D1-member opponent (team_seasons.division_member is what standings and ratings filter on). Division membership isn't known until later in the season, so filtering at pick time isn't possible. These grade normally; no special handling.

Completion Criteria

Every item below must be satisfied before proceeding to Phase 4.

  • Migration applies cleanly via supabase db reset
  • picks exists with both enums, the unique constraint, and all three indexes
  • Inserting a pick without season_id/sport_code populates them correctly from the game
  • RLS is enabled and authenticated has the four policies
  • A user cannot insert a pick for a game whose start_time has passed
  • A user cannot insert a pick for a game with status live, final, postponed or cancelled
  • A user cannot insert or update a pick with another user's user_id
  • A user cannot select another user's picks
  • A user can insert, update and delete their own pick on a future scheduled game
  • The unique constraint prevents two picks on the same game by the same user
  • src/lib/picks.ts exists with passing tests for: home win, away win, 0-0 draw, non-zero draw, shootout (→ draw), null scores, non-final status, and lock boundaries either side of start_time
  • npm run test passes

How to Validate

The security properties are the point of this phase — test them as an actual authenticated user, not as service_role, which bypasses RLS entirely and will make every check falsely pass.

  1. Apply the migration and confirm the schema: \d picks in psql, or list_tables.
  2. Pick a future game and a past game from the 2026 season: 
    select id, contest_date, start_time, status from games
where season_id = (select id from seasons where year = 2026)
order by start_time limit 5;
  3. In the Supabase SQL editor, impersonate an authenticated user: 
    set local role authenticated;
set local request.jwt.claims = '{"sub":"<user-uuid>","role":"authenticated"}';
  4. Happy path: insert a pick on a future scheduled game → succeeds. Update its outcome → succeeds. Delete it → succeeds.
  5. Late pick: insert on a game whose start_time is in the past → must fail with an RLS violation.
  6. Status gate: insert on a final game → must fail.
  7. Identity gate: insert with a different user_id → must fail.
  8. Read isolation: insert picks as two different users, then select * from picks as each — each sees only their own row.
  9. Trigger: confirm the inserted rows have correct season_id and sport_code without having supplied them.
  10. Race check: insert a pick on a game starting shortly, then update games set start_time = now() - interval '1 minute' and attempt to update the pick → must now fail.
  11. Run npm run test.
