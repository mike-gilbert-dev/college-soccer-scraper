Phase 1: Schema & Storage

Project: News Section Phase: 1 of 6 Depends on: None (first phase)

Overview

This phase lays the data foundation for the entire news feature: the articles table, the many-to-many join tables that tag articles to teams and players, a public Storage bucket for article images, and the Row Level Security (RLS) policies that let anonymous visitors read published articles while keeping drafts private. Nothing else can be built until this exists, so it comes first.

What Will Be Built

Migration: supabase/migrations/<timestamp>_articles.sql

Use the repo's timestamp convention (YYYYMMDDHHMMSS_articles.sql, a value greater than the latest existing migration 20260628000001). Create the following:

CREATE TABLE articles (
  id            bigserial   PRIMARY KEY,
  slug          text        NOT NULL UNIQUE,
  title         text        NOT NULL,
  subtitle      text,                         -- dek / summary line
  category      text,                         -- free-form label
  body_markdown text        NOT NULL DEFAULT '',
  hero_image_path text,                       -- object key in article-images bucket
  hero_image_url  text,                       -- resolved public URL (convenience)
  status        text        NOT NULL DEFAULT 'draft'
                            CHECK (status IN ('draft','published')),
  published_at  timestamptz,                  -- editable; set when first published
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX articles_published_idx
  ON articles (published_at DESC)
  WHERE status = 'published';
CREATE INDEX articles_status_idx ON articles (status);

Join tables (article ↔ entity tagging)

Both reference the bigserial id PKs (not the natural keys) for FK integrity. teams.id and players.id are both bigserial PRIMARY KEY (confirmed in 20260606000000_initial_schema.sql and 20260606000006_players.sql).

CREATE TABLE article_teams (
  article_id bigint NOT NULL REFERENCES articles (id) ON DELETE CASCADE,
  team_id    bigint NOT NULL REFERENCES teams (id)    ON DELETE CASCADE,
  PRIMARY KEY (article_id, team_id)
);

CREATE TABLE article_players (
  article_id bigint NOT NULL REFERENCES articles (id)  ON DELETE CASCADE,
  player_id  bigint NOT NULL REFERENCES players (id)   ON DELETE CASCADE,
  PRIMARY KEY (article_id, player_id)
);
CREATE INDEX article_teams_team_idx     ON article_teams (team_id);
CREATE INDEX article_players_player_idx ON article_players (player_id);

updated_at trigger

Add a BEFORE UPDATE trigger that sets updated_at = now() on articles (a small plpgsql function, SECURITY DEFINER SET search_path = '' to match the repo's convention in 20260606000005_profiles.sql).

Grants & RLS

Mirror the pattern in 20260606000001_permissions.sql. service_role gets full access (admin writes go through supabaseAdmin, which bypasses RLS but still needs the GRANT); anonymous/authenticated get public read of published rows only.

GRANT ALL ON TABLE articles, article_teams, article_players TO service_role;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO service_role;

ALTER TABLE articles        ENABLE ROW LEVEL SECURITY;
ALTER TABLE article_teams   ENABLE ROW LEVEL SECURITY;
ALTER TABLE article_players ENABLE ROW LEVEL SECURITY;

-- Anonymous visitors may read ONLY published articles (drafts stay hidden)
CREATE POLICY "public read published articles"
  ON articles FOR SELECT USING (status = 'published');

-- Join rows are readable by all; the parent article's RLS is what gates
-- visibility of a draft's tags in practice (a draft article won't be
-- selectable, so its tags are never joined for anon users).
CREATE POLICY "public read article_teams"   ON article_teams   FOR SELECT USING (true);
CREATE POLICY "public read article_players" ON article_players FOR SELECT USING (true);
Draft privacy: the public read policy on articles is the security boundary. Because admin CRUD runs server-side through supabaseAdmin (service_role, RLS-bypassing) and is gated by hooks.server.ts, admins can still read/write drafts. Never expose a browser-side (publishable-key) query path that could return drafts.

Migration: supabase/migrations/<timestamp+1>_article_images_bucket.sql

A separate migration (matches the repo habit of one bucket per file, e.g. 20260610000000_ncaa_raw_bucket.sql, 20260622000002_player_headshots.sql). Public bucket so the site serves images directly:

INSERT INTO storage.buckets (id, name, public)
VALUES ('article-images', 'article-images', true)
ON CONFLICT (id) DO NOTHING;

Implementation Notes

  • Migrations are applied via the Supabase MCP apply_migration tool (or npm run db:push if working against a linked local CLI). Prefer list_tables first to confirm the current state, then apply_migration with a descriptive name.
  • Slug is UNIQUE NOT NULL. Slug generation/uniqueness handling lives in the server layer (Phase 2); the DB just enforces the constraint.
  • No author field — the intake decided against a byline.
  • Follow the existing SQL style: lowercase keywords are used in newer migrations, uppercase in older ones — either is fine, but be internally consistent within the file.

Completion Criteria

Every item below must be satisfied before proceeding to Phase 2.

  • articles, article_teams, article_players tables exist with the columns, constraints, and indexes above.
  • status CHECK constraint rejects any value other than draft/published.
  • updated_at auto-updates on row UPDATE (verified with a manual update).
  • RLS is enabled on all three tables; the public policy on articles returns published rows only.
  • The article-images Storage bucket exists and is public.
  • Migrations are applied to the remote project and appear in list_migrations.

How to Validate

  1. Run list_tables (Supabase MCP) and confirm the three new tables with expected columns/FKs.
  2. Insert a draft row via execute_sql: 
    insert into articles (slug, title, body_markdown, status)
values ('test-draft', 'Test Draft', '# hi', 'draft');
  3. Simulate anonymous read — confirm the draft is not visible under the public policy. Using the Supabase SQL editor as the anon role (or a publishable-key query in the app later) should return 0 rows for select * from articles. As service_role it returns 1.
  4. Update the row to status='published', published_at=now() and confirm anon can now read it, and that updated_at changed.
  5. In the Supabase dashboard → Storage, confirm the article-images bucket exists and is marked Public.
  6. Clean up the test row: delete from articles where slug='test-draft';
