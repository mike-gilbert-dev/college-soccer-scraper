Phase 2: Server Data Layer & Image Upload

Project: News Section Phase: 2 of 6 Depends on: Phase 1 complete
⚠ Prerequisite: Phase 1 (Schema & Storage) must be complete — the tables and the article-images bucket must exist.

Overview

This phase builds the reusable server-side plumbing every UI phase consumes: typed query helpers for reading and writing articles, the Markdown→HTML render+sanitize helper, slug generation, and the admin-gated image upload endpoint. Doing this once, server-side, keeps the admin UI (Phase 3) and public pages (Phases 4–5) thin and consistent, and guarantees drafts never leak through a browser query path.

What Will Be Built

1. Dependencies

Add two packages: a Markdown parser and an HTML sanitizer (admins are trusted, but sanitizing SSR-rendered HTML is cheap insurance and lets us safely render any pasted content).

npm i marked sanitize-html
npm i -D @types/sanitize-html
marked is synchronous and dependency-light; sanitize-html runs server-side (Node) which fits our SSR render path. Do the render on the server so no parser ships to the browser.

2. src/lib/server/markdown.ts

A single exported function renderMarkdown(md: string): string that runs marked then sanitizeHtml with an allowlist that includes headings, paragraphs, lists, a, img (with src/alt/title), blockquote, code/pre, strong/em, and figure/figcaption. Force a[target=_blank] + rel="noopener" for external links. This is the ONLY place Markdown becomes HTML.

3. src/lib/server/articles.ts

Typed helpers used by loaders and endpoints. Reads for the public site use event.locals.supabase (publishable key + RLS, so only published rows return); admin reads/writes use supabaseAdmin. Export at minimum:

  • listPublishedArticles(client, { offset, limit }) — returns published articles ordered by published_at DESC, selecting card fields (id, slug, title, subtitle, category, hero_image_url, published_at). Uses .range(offset, offset+limit-1) and returns { rows, hasMore } (fetch limit+1 to detect more, or use an exact count).
  • getPublishedArticleBySlug(client, slug) — single published article incl. body_markdown and joined related teams/players (name, logo/slug, ncaa ids for links).
  • getArticleForAdmin(slug_or_id) — via supabaseAdmin, any status, incl. related team/player ids for the editor.
  • listArticlesForAdmin({ status? }) — via supabaseAdmin, all statuses, newest first, for the admin index.
  • createArticle(input) / updateArticle(id, input) — via supabaseAdmin; upsert the row, then reconcile article_teams/article_players (delete-then-insert the provided id sets in a best-effort transaction-like sequence). On first transition to published with no published_at, set published_at = now() unless an explicit value was supplied.
  • deleteArticle(id) — via supabaseAdmin (cascade removes join rows).
  • uniqueSlug(base) — slugify a title (reuse the deriveSlug approach already in src/routes/admin/+page.svelte) and append -2, -3… until unique against articles.slug.

4. Image upload endpoint: src/routes/api/admin/news/upload/+server.ts

Admin-gated POST that accepts a multipart/form-data file, uploads it to the article-images bucket via supabaseAdmin.storage, and returns { path, url } (public URL from getPublicUrl). Used for BOTH the hero image and inline body images (Phase 3 calls it and inserts ![alt](url) at the cursor).

  • Object key: <yyyy>/<mm>/<uuid>.<ext> (e.g. crypto.randomUUID()). Content-addressed-ish, avoids collisions.
  • Validate: content-type starts with image/; reject > ~8 MB; allow jpg/png/webp/gif.
  • Set cacheControl: '31536000' and upsert: false.

5. Register the admin path in src/hooks.server.ts

Add '/api/admin' to the ADMIN_PATHS array so the upload endpoint (and any future admin API) is gated exactly like /admin and /api/scrape.

Implementation Notes

  • Runes mode is enforced repo-wide, but this phase is .ts only — no Svelte components yet.
  • Never read drafts through locals.supabase; that client uses the publishable key and RLS will (correctly) hide them. Admin reads must use supabaseAdmin.
  • SUPABASE_SERVICE_ROLE_KEY is already wired into src/lib/server/supabase-admin.ts; reuse that singleton, don't create a new client.
  • Keep the related-entity reconcile simple: delete from article_teams where article_id=? then bulk insert the new set. Same for players. Acceptable because edits are infrequent and admin-only.
  • Types: optionally regenerate types via the Supabase MCP generate_typescript_types, or hand-write a small Article interface in articles.ts. Match how the rest of the app types Supabase rows (the homepage hand-writes interfaces).

How to Validate

  1. npm run check passes with no new errors.
  2. Unit-poke renderMarkdown from a scratch script: feed <img src=x onerror=alert(1)>## Hi and confirm the output has the heading but no onerror.
  3. With the dev server running and signed in as an admin, POST an image to /api/admin/news/upload (e.g. via the browser devtools or a small fetch) and confirm a { path, url } response whose url loads the image.
  4. Sign out (or use an incognito session) and POST again — confirm you're redirected/blocked by the admin gate.
  5. Temporarily call listPublishedArticles(locals.supabase, {offset:0,limit:5}) from a scratch loader and confirm it returns only published rows (create one published + one draft to verify the draft is excluded).
